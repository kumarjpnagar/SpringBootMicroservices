1️⃣ CompletableFuture in Java (Async Programming)
CompletableFuture is part of Java java.util.concurrent package used for asynchronous and non-blocking programming.

It helps to run tasks in background threads without blocking the main thread.

Step 1 — Problem Without CompletableFuture (Blocking)
Example: Calling 3 APIs sequentially

public class BlockingExample {

    public static String getUser() throws InterruptedException {
        Thread.sleep(2000);
        return "User";
    }

    public static String getOrders() throws InterruptedException {
        Thread.sleep(2000);
        return "Orders";
    }

    public static void main(String[] args) throws Exception {

        String user = getUser();
        String orders = getOrders();

        System.out.println(user + " " + orders);
    }
}

Execution Time

User API = 2 sec
Orders API = 2 sec

Total = 4 sec
This is slow because calls are sequential.

Step 2 — CompletableFuture Async Execution
Now both APIs run parallel.

import java.util.concurrent.CompletableFuture;

public class AsyncExample {

    public static String getUser() {
        try { Thread.sleep(2000); } catch (Exception e) {}
        return "User";
    }

    public static String getOrders() {
        try { Thread.sleep(2000); } catch (Exception e) {}
        return "Orders";
    }

    public static void main(String[] args) throws Exception {

        CompletableFuture<String> userFuture =
                CompletableFuture.supplyAsync(() -> getUser());

        CompletableFuture<String> orderFuture =
                CompletableFuture.supplyAsync(() -> getOrders());

        String result = userFuture.get() + " " + orderFuture.get();

        System.out.println(result);
    }
}
Execution

User API = 2 sec
Orders API = 2 sec

Total = 2 sec
Now parallel execution happens.

Step 3 — Chaining CompletableFuture
Example

User → Orders → Payment
CompletableFuture.supplyAsync(() -> "User")
        .thenApply(user -> user + " Orders")
        .thenApply(result -> result + " Payment")
        .thenAccept(System.out::println);
Output

User Orders Payment

Step 4 — Combine Multiple 

Example: Fetch User + Orders

CompletableFuture<String> user =
        CompletableFuture.supplyAsync(() -> "User");

CompletableFuture<String> order =
        CompletableFuture.supplyAsync(() -> "Orders");

CompletableFuture<String> result =
        user.thenCombine(order, (u, o) -> u + " " + o);

System.out.println(result.get());
Output

User Orders

Step 5 — Error Handling:

CompletableFuture.supplyAsync(() -> {
    if(true) throw new RuntimeException("Error");
    return "Success";
})
.exceptionally(ex -> "Fallback Response")
.thenAccept(System.out::println);
Output

Fallback Response

1️⃣ Circuit Breaker Concept
Circuit Breaker protects systems from cascading failures.

States
CLOSED → OPEN → HALF-OPEN
CLOSED
All requests go through
OPEN
Failures exceed threshold
Requests are blocked
Fallback is returned
HALF-OPEN
Few requests allowed to test recovery
If success → CLOSED
If failure → OPEN

7️⃣ Order Controller with Circuit Breaker
@RestController
@RequestMapping("/orders")
public class OrderController {

    @Autowired
    RestTemplate restTemplate;

    @GetMapping("/{id}")
    @CircuitBreaker(name="paymentService", fallbackMethod="fallbackMethod")
    public String placeOrder(@PathVariable String id){

        String response =
                restTemplate.getForObject(
                        "http://localhost:8081/payment/"+id,
                        String.class);

        return "Order Created : " + response;
    }

    public String fallbackMethod(String id, Exception ex){

        return "Payment service unavailable. Order placed in pending state";
    }
}

1️⃣5️⃣ Interview Answer (Best Explanation)
If interviewer asks:

What is Circuit Breaker in Microservices?

You can say:

Circuit Breaker is a fault tolerance pattern that prevents cascading failures in microservices.
When the failure rate exceeds a configured threshold, the circuit moves from CLOSED to OPEN and stops calling the failing service.
After a wait duration, it enters HALF-OPEN state to test if the service has recovered.
In Spring Boot we implement it using Resilience4j with @CircuitBreaker annotation and fallback methods.

package com.demo.order.controller;

import io.github.resilience4j.circuitbreaker.annotation.CircuitBreaker;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.web.bind.annotation.*;
import org.springframework.web.client.RestTemplate;

@RestController
@RequestMapping("/orders")
public class OrderController {

 @Autowired
 RestTemplate restTemplate;

 @GetMapping("/{id}")
 @CircuitBreaker(name="paymentService",fallbackMethod="fallback")
 public String placeOrder(@PathVariable String id){

  String paymentResponse =
   restTemplate.getForObject(
    "http://localhost:8081/payment/"+id,
    String.class
   );

  return "Order Created : " + paymentResponse;
 }

 public String fallback(String id,Exception ex){

  return "Payment Service Down - Order in Pending State";
 }

}

6️⃣ Global Exception Handler
GlobalExceptionHandler.java
package com.demo.exception;

import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.*;

import jakarta.servlet.http.HttpServletRequest;

import java.time.LocalDateTime;

@ControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(UserNotFoundException.class)
    public ResponseEntity<ErrorResponse> handleUserNotFound(
            UserNotFoundException ex,
            HttpServletRequest request){

        ErrorResponse error = new ErrorResponse(
                LocalDateTime.now(),
                HttpStatus.NOT_FOUND.value(),
                "User Not Found",
                ex.getMessage(),
                request.getRequestURI()
        );

        return new ResponseEntity<>(error, HttpStatus.NOT_FOUND);
    }

    @ExceptionHandler(Exception.class)
    public ResponseEntity<ErrorResponse> handleGenericException(
            Exception ex,
            HttpServletRequest request){

        ErrorResponse error = new ErrorResponse(
                LocalDateTime.now(),
                HttpStatus.INTERNAL_SERVER_ERROR.value(),
                "Internal Server Error",
                ex.getMessage(),
                request.getRequestURI()
        );

        return new ResponseEntity<>(error, HttpStatus.INTERNAL_SERVER_ERROR);
    }
}

What happens when consumer joins a group

When a consumer joins a consumer group in Apache Kafka, Kafka performs a group coordination and partition assignment process called Rebalancing. This ensures that each partition of a topic is assigned to exactly one consumer in that group.

Below is the step-by-step internal working (hands-on explanation).

1️⃣ Consumer Sends Join Request
When a consumer starts (for example in Spring Boot using @KafkaListener), it sends a JoinGroup request to the Group Coordinator Broker.

Example configuration:

spring:
  kafka:
    consumer:
      group-id: order-group
      bootstrap-servers: localhost:9092
Flow:

Consumer starts
      |
JoinGroup request
      |
Kafka broker (Group Coordinator)
The broker responsible for managing the consumer group is called the Group Coordinator.

2️⃣ Group Coordinator Registers Consumer
Kafka assigns a unique member ID to the consumer.

Example:

Consumer instance → consumer-1
Assigned member.id → order-group-1a2b
Now Kafka knows:

Group: order-group
Members: consumer1

3️⃣ Kafka Triggers Rebalance
Whenever a consumer joins or leaves a group, Kafka performs Rebalancing.

Rebalance means:

Redistribute partitions across consumers
Example:

Topic: order-topic
Partitions: 3
Consumers: 1
Assignment:

Consumer1 → Partition0,1,2
Now a new consumer joins.

Consumers: 2
Rebalance happens.

New assignment:

Consumer1 → Partition0
Consumer2 → Partition1,2

4️⃣ Partition Assignment Strategy
Kafka uses a partition assignor algorithm.

Common strategies:

Strategy	Behaviour
RangeAssignor	sequential partition assignment
RoundRobinAssignor	evenly distribute partitions
StickyAssignor	minimize movement during rebalance
Example:

Topic partitions: 6
Consumers: 3
Round robin assignment:

Consumer1 → P0,P3
Consumer2 → P1,P4
Consumer3 → P2,P5

5️⃣ Consumers Receive Partition Assignment
After rebalance, Kafka sends SyncGroup response.

Consumer receives its partitions.

Example:

Consumer1 assigned partitions: 0,3
Consumer2 assigned partitions: 1,4
Consumer3 assigned partitions: 2,5
Now consumers start polling messages.

Payload push or we get acks then push

In Apache Kafka, the producer always pushes the payload first, and ACK (acknowledgment) is received after the broker processes the message.
So the correct sequence is:

Producer PUSHES payload → Broker processes message → Broker sends ACK
Not:

ACK first → then payload

In event-driven communication, microservices interact by publishing and consuming events rather than calling each other directly. 1️⃣ Kafka Retry Topics (Hands-On)

Retry topics are used when a consumer temporarily fails to process a message.

Instead of immediately failing, the message is retried after some delay.

Step 2 — Producer

    KafkaTemplate<String,String> kafkaTemplate;

        kafkaTemplate.send("orders", order);
    }
}

Step 3 — Consumer With Retry

@Service
public class OrderConsumer {

    @Autowired
    KafkaTemplate<String,String> kafkaTemplate;

    @KafkaListener(topics = "orders", groupId = "order-group")
    public void consume(String message){

        try{
            processOrder(message);
        }
        catch(Exception e){

            kafkaTemplate.send("orders_retry", message);
        }
    }

    private void processOrder(String order){
        throw new RuntimeException("Temporary failure");
    }
}

6️⃣ Outbox Publisher Service

Reads DB events and publishes to Kafka.

@Service
public class OutboxPublisher {

@Autowired
OutboxRepository repository;

@Autowired
KafkaTemplate<String,String> kafkaTemplate;

@Scheduled(fixedDelay = 5000)
public void publish(){

List<OutboxEvent> events = repository.findByStatus("NEW");

for(OutboxEvent event : events){

kafkaTemplate.send("order-created",event.getPayload());

event.setStatus("SENT");

repository.save(event);

}

}

}

Below is a deep hands-on explanation of ISR (In-Sync Replicas) in Apache Kafka including architecture, replication flow, broker behavior, configuration, and failure scenarios. This is one of the most important Kafka internals.

1️⃣ What is ISR (In-Sync Replica)

ISR = In-Sync Replicas

It is the set of replicas that are fully synchronized with the leader partition.

Every partition has:

1 Leader

N Followers

Example topic:

Topic: orders
Replication Factor = 3

Partition replication:

Partition-0

Leader → Broker1
Follower → Broker2
Follower → Broker3

ISR set:

ISR = {Broker1, Broker2, Broker3}

Meaning:

✔ All replicas are fully synchronized with the leader.

2️⃣ Why ISR Exists

Without ISR, Kafka could elect a replica with stale data as leader.

ISR ensures:

✔ strong durability
✔ consistent replication
✔ safe leader election

Only replicas inside ISR can become leader.

6️⃣ ISR Shrink Scenario

If follower lags behind, Kafka removes it from ISR.

Example:

Partition0

Leader → Broker1
Follower → Broker2
Follower → Broker3

Suppose Broker3 becomes slow.

Replication lag:

Leader offset = 100
Broker3 offset = 70

Kafka removes it.

New ISR:

ISR = {Broker1, Broker2}

Broker3 still stores replica but not trusted.

7️⃣ ISR Expand Scenario

When follower catches up again:

Broker3 offset = 100

Kafka adds it back.

New ISR:

ISR = {Broker1, Broker2, Broker3}
8️⃣ ISR Timeout Configuration

Important configuration:

replica.lag.time.max.ms=10000

Meaning:

If follower doesn't fetch within 10 seconds, it is removed from ISR.

9️⃣ Producer ACK Behavior with ISR

Producer config:

acks=all

Flow:

Producer
   │
   ▼
Leader writes message
   │
   ▼
Replicas in ISR replicate message
   │
   ▼
Leader sends ACK to producer

ACK happens only when all ISR replicas confirm.

This guarantees no data loss.

🔟 min.insync.replicas (Very Important)

Kafka setting:

min.insync.replicas=2

Meaning:

At least 2 ISR replicas must acknowledge writes.

Example scenario:

Replication factor = 3
min.insync.replicas = 2

Case:

ISR = {Broker1, Broker2}

Writes allowed.

But if:

ISR = {Broker1}

Producer will receive error:

NOT_ENOUGH_REPLICAS

This prevents data loss.
