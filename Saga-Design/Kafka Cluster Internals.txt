Welcome to Chapter 1: Kafka Fundamentals. Let's break down the core concepts, architecture, and practical first steps of Apache Kafka, keeping the classic Zookeeper-based metadata management at the center of our discussion (while noting the modern transition at the end).

1. Definition:

Apache Kafka is a distributed event streaming platform designed for high-throughput, fault-tolerant, publish-subscribe messaging.

Unlike traditional message queues (which delete messages after consumption), Kafka is a durable log. It retains messages based on a time/size retention policy, allowing consumers to "replay" past events. It decouples data pipelines, enabling asynchronous communication between services.

3. Deep Dive: Publish-Subscribe Architecture Overview:

In Kafka's implementation of pub/sub:

Producers publish messages to Topics. They don't care who reads them.

Topics are divided into Partitions (ordered, immutable sequences of records). Each record gets a unique Offset.

Consumers subscribe to Topics. They work within Consumer Groups. If you have 4 partitions and 4 consumers in the same group, each consumer reads exactly 1 partition (parallelism). If you have 2 groups, both groups read all 4 partitions independently (broadcast).

Zookeeper (in this classic setup) holds the crucial "source of truth": which broker is the controller, which replica is the In-Sync Replica (ISR) leader, and stores the /brokers/ids and /consumers (offsets in older versions).

4. Real-Time Usage (Industry Use Cases)

Event-Driven Microservices: Service A publishes an "Order Placed" event. Payment, Inventory, and Notification services consume it independently.

Real-Time Analytics Pipelines: Ingesting clickstream data from websites into Kafka, then feeding it into Apache Flink/Spark for real-time dashboards (e.g., monitoring viral content).

Log Aggregation: Centralizing logs from thousands of servers into a single Kafka topic, which then sinks into Elasticsearch for observability.

Change Data Capture (CDC): Using Debezium to capture row-level changes from a PostgreSQL database and publishing them to Kafka, enabling caches (like Redis) or search indexes (like Elasticsearch) to stay in sync instantly.

⚠️ A Note on the Future: KRaft (No Zookeeper):

As of Apache Kafka 3.0+, Zookeeper is officially deprecated for metadata management and will be removed entirely in Kafka 4.0.

In modern Kafka setups (KRaft - Kafka Raft), Zookeeper is replaced by a built-in Raft quorum within the Kafka brokers themselves. They now store metadata directly in internal topics (like __cluster_metadata), simplifying the architecture by removing an external dependency. However, the core Publish-Subscribe data flow (Producers → Brokers → Consumers) remains completely unchanged—only the metadata plane has evolved.

Welcome to Chapter 2 — Topics, Partitions & Offsets. This is the most critical chapter for understanding Kafka’s scalability and ordering semantics.

Let’s visualize exactly what a Topic looks like under the hood, why Offsets are immutable, and how you control data distribution via CLI.

1. Definition:

Topic: A logical category or feed name to which records (messages) are published. It is similar to a table in a database, but without schema constraints.

Partition: A physical, ordered, immutable sequence of records. A Topic is split into Partitions to allow parallel processing.

Offset: A unique, sequential integer ID assigned to each record within a specific partition. Offsets are immutable—once a record is written, its offset never changes.

Crucial Rule: Kafka guarantees order strictly within a single partition, but not across partitions in the same topic. If you need total order for all events, you must use only 1 partition (sacrificing parallelism).

4. Real-Time Usage (Why these concepts matter)
Ordering Guarantee: In financial transactions, you must process events for Account A in the exact chronological order (Debit before Credit). By using the Account_ID as the message key, Kafka forces all events for Account A into the same partition, giving you strict ordering.

Horizontal Scaling (Parallelism): A social media platform handles 1 million events/sec. By splitting a user-actions topic into 50 partitions, they can spin up 50 consumer instances in the same group—each consuming one partition—processing the load 50x faster.

Immutable Offsets for Replay (Data Warehousing): If your ETL pipeline crashes at 2:00 AM, you don't lose data. You simply reset your consumer group's committed offset back 2 hours (e.g., --to-datetime 2026-07-12T00:00:00.000) and replay the exact same immutable records to rebuild your Snowflake/BigQuery tables without asking the producer to resend.

Storage Tiering: Because partitions are logs, you configure retention (e.g., 7 days). Old partitions with old offsets are automatically deleted, giving you a bounded, manageable storage footprint.

5. ⚠️ Critical Internal Mechanics (Controller & Partition Leaders)

Let’s go deep under the hood. While Chapter 2 covered the logical view, the internals are where Kafka's legendary performance and durability actually come from.

Here is the complete mechanical breakdown of how Topics, Partitions, and Offsets work inside a Kafka broker.

1. Physical Storage Internals: The Partition is NOT a Single File
When you create a topic with 3 partitions, Kafka does not create one giant file per partition. Instead, it splits each partition into Segments on disk.

Directory Structure on Disk (Linux):
/var/lib/kafka/data/topic-orders/partition-0/

Inside that folder, you will find:

00000000000000000000.log (The actual message data)

00000000000000000000.index (Offset → Byte Position mapping)

00000000000000000000.timeindex (Timestamp → Offset mapping)

00000000000000000123.log (Segment 2, starting at offset 123)

00000000000000000123.index

...

Why Segments?:

If you had a single 1 TB file, deleting old messages would be impossibly slow. Instead, Kafka rolls over to a new segment when the current one hits log.segment.bytes (default 1GB) or log.roll.hours (default 7 days). When retention expires, Kafka deletes entire segment files in O(1) time—just an unlinking operation from the filesystem.

2. The Magic of the Index File (Offset Lookup)
Consumers frequently ask: "Give me data from Partition 0, starting at Offset 5,000."

How does Kafka find Offset 5,000 instantly in a 1GB .log file?

The .log file contains raw messages of variable sizes (compressed, different JSON payloads).

The .index file is a sparse hash map (not a full index, to save memory).

It maps every N bytes (default log.index.interval.bytes = 4096) to the exact byte position in the .log file.

Lookup Flow (Binary Search + Scan):

Kafka performs a binary search on the .index file to find the closest entry before Offset 5,000 (e.g., Offset 4,990 → Byte Position 1,024,000).

It jumps directly to Byte 1,024,000 in the .log file.

It reads sequentially (scanning) from 4,990 to 5,000 (just 10 records) until it finds the exact message.
Because of the sparse index, disk seeks are minimized, and the final scan is tiny.

3. Replication Internals: LEO (Log End Offset) and HW (High Watermark)
This is where partitions become fault-tolerant. Each partition has a Leader and Followers (ISR - In-Sync Replicas). Internally, every broker keeps two crucial numbers for every partition replica:

LEO (Log End Offset): The offset of the next message that will be written to that specific replica. (e.g., If the last message was offset 99, LEO = 100).

HW (High Watermark): The highest offset that has been committed to all ISR replicas. Consumers can only read messages up to the HW. Messages beyond HW are considered "uncommitted" and invisible to consumers.

The Write Path Internals (with acks=all):

Producer sends a batch of messages to the Partition Leader.

Leader appends the messages to its local .log file and updates its LEO immediately.

Leader forwards the messages to all Follower brokers in the ISR. Followers fetch these updates and write to their own logs, updating their LEO.

Followers send an acknowledgment (ACK) back to the Leader, reporting their new LEO.

When the Leader sees that all ISR followers have updated their LEOs to the new batch, it moves the HW forward.

Only after the HW advances does the Leader send an ACK back to the Producer.

If the Leader crashes: The controller picks the Follower with the highest LEO that is still within the ISR. Since this Follower had caught up to the HW, zero data is lost (provided min.insync.replicas is set correctly).

4. Zero-Copy & Page Cache (Why Kafka is so fast)

Internally, Kafka completely bypasses the JVM heap for message storage.

OS Page Cache: When the Leader writes a message to disk, the Linux OS stores it in the Page Cache (RAM) first. Kafka does not call fsync immediately (unless forced). This means most writes are just memory copies.

Zero-Copy Reads: When a Consumer requests data, Kafka uses a Linux system call (sendfile()). Instead of copying data from Disk → Page Cache → Application Buffer → Socket Buffer, it copies directly from Page Cache → Socket Buffer (Network Card). This eliminates CPU overhead and halves memory usage, allowing Kafka to saturate 10 GbE networks on standard hardware.

5. Log Compaction (A Special Internal Behavior)

While regular retention deletes old data based on time/size, Log Compaction deletes based on keys.

Internally, the Kafka background thread (the "Cleaner") iterates over the partition segments. It maintains a map of the latest offset for every unique key in the partition.
It then rewrites the .log file, keeping only the latest message for each key, and deleting all older versions. This is extremely useful for KTable state restoration in Kafka Streams, where you only care about the current state (e.g., the latest user profile), not the history.

6. Consumer Offset Management (The __consumer_offsets Internal Topic)

When you commit an offset (e.g., "Group inventory read up to Partition 0, Offset 50"), Kafka does not store it in Zookeeper (in modern versions). It stores it in an internal, compacted topic named __consumer_offsets.

This topic has 50 partitions by default.

The key for a message is: GroupID + Topic + Partition (e.g., inventory_orders_0).

The value is the committed offset (e.g., 50).
Because this topic is log-compacted, Kafka retains only the latest committed offset for every consumer group/partition pairing. If your consumer restarts, it reads this topic to know exactly where to resume.

7. Internal Partition Assignment Algorithms

When a new consumer joins a group, the Group Coordinator (a designated broker) triggers a rebalance. Internally, it uses one of these assignors:

Range Assignor (Default pre-3.0) : Sorts partitions numerically and consumers alphabetically. It assigns contiguous ranges. (Prone to skew if consumers are uneven).

Round-Robin Assignor: Assigns partitions one-by-one to consumers in a circular fashion.

Sticky Assignor (Modern default): Assigns partitions evenly and minimizes partition movement when a rebalance occurs. It tries to keep the previous assignments intact, only moving the minimum number of partitions to accommodate the new consumer.

8. The "Controller" Election Internals:

In the classic Zookeeper setup, the Controller is a specific broker that watches /brokers/ids in Zookeeper. When a broker crashes, Zookeeper fires a watch event. The Controller instantly:

Reads the ISR list for all partitions where the dead broker was the Leader.

Updates the Leader metadata to a new ISR member.

Sends LeaderAndIsr requests to all alive brokers via internal RPCs.

This entire failover happens in milliseconds (typically < 5 seconds).

In the new KRaft mode, this logic is internalized inside the brokers using the Raft consensus protocol, removing Zookeeper entirely, but the conceptual mechanics (Leader election, ISR management) remain identical.

Summary of Internal Mechanics:

Component	Internal Reality->

Topic	A logical namespace; physically just a folder on disk containing multiple partition directories.
Partition	A directory containing a sequence of immutable segment files (.log + .index + .timeindex).
Offset	An 8-byte signed long; sequential per partition; maps to a physical byte position via sparse indexing.
Write	Append to leader's page cache; wait for ISR follower LEOs; advance HW; send ACK.
Read	Consumer sends fetch request; broker uses binary search on index to find segment; uses sendfile() zero-copy to stream bytes to the network.
Retention	Background threads either delete old segment files (time/size) or compact the log (key-based cleanup).
Offset Commit	Stored as a message in __consumer_offsets internal topic (compacted), not in-memory.
This internal architecture is precisely why Kafka can handle millions of writes per second while providing strict ordering, exactly-once semantics, and zero-data-loss failover.

3. Deep Dive: Sticky Partitioning (Why it Matters):

The Old Way (Pre-2.4): If key=null, the Producer did Round-Robin (Partition 0, then 1, then 2, etc.). This caused many small batches: since data was spread across all partitions simultaneously, each batch took a long time to fill up, resulting in higher latency and more network requests.

The Modern Way (Sticky Partitioner - Default):
When key=null, the Producer picks one partition at random and "sticks" to it. It sends all records to that single partition until that partition's batch is completely full (batch.size) or linger.ms expires. Only then does it switch to a new partition.

Why it's faster:

Batches are filled to the maximum 16KB much faster, reducing the number of ProduceRequests sent to the broker.

Fewer requests mean lower per-request overhead and reduced CPU usage on both client and broker, improving overall throughput by up to 30% compared to round-robin.

4. The acks Tradeoffs (Durability vs. Latency):

The acks (Acknowledgments) configuration dictates when the broker sends a response back to the Producer. This is the most critical decision for data safety.

Setting	Description	Producer Wait For	Data Loss Risk	Throughput
acks=0	Fire-and-forget. The Producer sends the batch and immediately considers it successful, without waiting for any response from the broker.	Nothing	Extremely High. If the broker crashes or the network drops, the data is gone forever. The Producer won't even know.	Maximum (Ideal for high-volume metrics/logs where loss is acceptable).
acks=1	Leader ACK. The Producer waits only for the Partition Leader to write the data to its local log (Page Cache). It does not wait for followers.	Leader broker's local write.	Moderate. If the Leader crashes immediately after sending the ACK, but before followers replicate, the data is lost when a new leader is elected.	High (Default for many microservices).
acks=all
(or -1)	ISR ACK. The Producer waits for the Leader AND all In-Sync Replicas (ISR) to write the data to their logs.	All replicas in the ISR.	Zero (Theoretically). Data is only committed after it is fully replicated. Use with min.insync.replicas=2 to ensure at least one follower holds the data before the leader acks.	Lowest (Adds network round-trip latency to followers). Crucial for financial transactions.

buffer.memory (default 32MB): Total memory the Producer can use to batch records. If the Producer sends faster than the broker can accept, and this buffer fills up, send() will block or throw an exception.

2. Deep Dive: How Idempotence Management Works Internally

Without idempotence (enable.idempotence=false):
The Producer sends a batch to the broker. The broker writes it to disk, sends an ACK, but the ACK gets lost in transit. The Producer times out and retries the batch. The broker writes it again → Duplicate messages (and potential offset gaps).

With Idempotence (enable.idempotence=true):

Component	Internal Mechanism:

Producer ID (PID)	On startup, the Producer asks the broker for a unique 64-bit PID (valid for the entire session).
Sequence Numbers	For every partition this Producer writes to, it maintains a monotonically increasing sequence number (starting at 0).
Broker Side Cache	The broker maintains a cache of (PID, Partition) -> LastAcknowledgedSequenceNumber in memory.
Validation Logic	When the broker receives a new batch:
1. If seq_num == last_seq + 1 → ACCEPT (New data).
2. If seq_num == last_seq → ACCEPT, but DO NOT APPEND (Duplicate, send ACK anyway).
3. If seq_num < last_seq → REJECT (Out of order).
4. If seq_num > last_seq + 1 → REJECT (Missing data).

Retry Behavior	Since retries keep the exact same Sequence Number, the broker identifies them as duplicates and responds with success without corrupting the log.
Broker Restarts	If the broker crashes and a new leader is elected, the PID/Sequence cache is reset. The Producer will receive an error indicating the sequence number is out of range. The Producer automatically resets its PID (fetches a new one) and starts the sequence from 0 again.

5. The "Idempotence Pitfall" (When it doesn't cover you):

Idempotence only protects against Producer-induced duplicates (caused by retries). It does not protect against:

Manual Duplicates: If your application logic calls producer.send() twice for the same event (e.g., a loop bug), the PID/Sequence numbers will be different (because it's a new send call, sequence increments), so the broker will append both.

Cross-Session Duplicates: If the Producer crashes and restarts, it gets a new PID. The old broker cache drops the old PID's state after a few minutes. If the old Producer had pending messages that were never acked and the new Producer resends them, they might be written twice if the old one eventually recovers. (Solution: Use Transactional Producers + Idempotence for true cross-session exactly-once).

Welcome to Chapter 4 — Consumers & Consumer Groups. We shift from writing data to reading it. This chapter covers the mechanics of parallel processing, offset tracking, and crucially—how to handle failed messages, poison pills, and partition issues in production, all while maintaining idempotency on the read side.

1. Definition
Consumer: A client application that reads records from Kafka topics.

Consumer Group: A set of consumers working together to consume a topic. Kafka guarantees that each partition in the topic is assigned to exactly one consumer in the group (1:1 mapping). This allows parallel processing.

Group Coordinator: A broker responsible for managing consumer group membership, handling rebalances, and committing offsets.

__consumer_offsets: An internal, compacted Kafka topic that stores the committed offsets for every (Group, Topic, Partition) tuple.

Partition Assignment: The process of distributing partitions among consumers in a group. If you have more consumers than partitions, the excess consumers sit idle.

3. Handling Failed Messages & Poison Pills
A "Poison Pill" is a message that the consumer cannot process, usually due to:

Deserialization errors (corrupted JSON, AVRO schema mismatch).

Logic errors (division by zero, invalid business state).

If you simply let the consumer throw an exception, it will stop processing, the poll loop will break, and the consumer will eventually be kicked out of the group (rebalance).

Production-Grade Solutions:

Catch, Log, and Commit (Skip) - For non-critical data.

Dead Letter Queue (DLQ) - Send the raw failed message to a separate "dead-letter" topic for manual inspection.

Pause & Resume - If the issue is systemic (e.g., downstream DB is down), pause the partition to stop the flood, then resume later.

Code Example: Handling Deserialization Failure

java
while (true) {
    ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(1000));
    for (ConsumerRecord<String, String> record : records) {
        try {
            // Simulated processing
            processOrder(record.value());
            // If successful, we commit after the batch.
        } catch (JsonProcessingException e) {
            // LOG THE POISON PILL!
            System.err.printf("❌ Poison Pill! Topic: %s, Partition: %d, Offset: %d, Value: %s%n",
                    record.topic(), record.partition(), record.offset(), record.value());

            // OPTION A: SKIP IT. Commit this offset manually to move forward.
            // We'll use asynchronous commit to not block the loop.
            consumer.commitSync(Map.of(
                new TopicPartition(record.topic(), record.partition()),
                new OffsetAndMetadata(record.offset() + 1)
            ));
            
            // OPTION B: Send to Dead Letter Queue.
            // deadLetterProducer.send(new ProducerRecord<>("orders-dlq", record.value()));
        }
    }
    // Commit the highest offsets processed successfully.
    consumer.commitSync();
}

4. Consumer-Side Idempotency (Exactly-Once Processing)

Crucial Distinction: While Producer idempotence prevents duplicates from retries, Consumer idempotence is an application-layer pattern. Kafka itself does not deduplicate messages on the read side. A consumer can see duplicates if:

The Producer retries and writes the same message twice (without idempotence).

The Consumer processed a message, committed the offset, but the commit failed. On rebalance, it re-reads and re-processes the same message.

The Solution - Idempotent Writes: Ensure your processing logic is idempotent.

Database Upserts: Use a primary key (e.g., event_id) in your DB. Writing the same INSERT ON DUPLICATE KEY UPDATE twice yields the same final state.

External Deduplication Cache: Before processing, check a Redis cache for event_id. If it exists, skip processing; if not, process and store the ID with a TTL.

Kafka Transactions + read_committed: Set the consumer config isolation.level=read_committed. This ensures the consumer only reads messages that were committed by a transactional producer, masking aborted transactions and duplicates produced by retries (when combined with idempotent producers).

5. Partition Issues: Rebalancing & Stuck Consumers
Problem 1: Processing takes too long (Stuck Consumer)

The consumer must call poll() within max.poll.interval.ms (default 5 minutes).

If processing a batch takes longer, the consumer won't poll. The Group Coordinator assumes it's dead, leaves the group, and triggers a rebalance, reassigning partitions to other consumers.

Fix:

Increase max.poll.interval.ms.

OR, use the Background Processing Pattern: poll() frequently to keep the group alive, but push records to a local thread pool for async processing. Warning: If the thread pool fails, offsets are already committed.

Problem 2: Static Group Membership (Avoiding Rebalances on Restart)
If you restart a fleet of consumers, they constantly trigger rebalances. Use group.instance.id to make consumers static. The coordinator allows them to rejoin without dropping their partitions immediately.

C. The Idempotent Consumer (End-to-End)
Create IdempotentOrderConsumer.java. This class demonstrates:

Manual commits (enable.auto.commit=false).

Poison Pill handling (Skips bad records without crashing).

Idempotent processing (Deduplication via ConcurrentHashMap).

Rebalance Listeners (Logs partition assignments and commits before revocation).

java
package com.kafka.consumer;

import com.fasterxml.jackson.databind.ObjectMapper;
import com.kafka.model.Order;
import org.apache.kafka.clients.consumer.*;
import org.apache.kafka.common.TopicPartition;
import org.apache.kafka.common.serialization.StringDeserializer;

import java.time.Duration;
import java.util.*;
import java.util.concurrent.ConcurrentHashMap;

public class IdempotentOrderConsumer {

    private static final String TOPIC = "orders";
    private static final String GROUP_ID = "inventory-group";

    // Simulates an external idempotent storage (e.g., Redis/Database Primary Key)
    // Stores successfully processed Order IDs to skip duplicates.
    private static final ConcurrentHashMap<String, Boolean> PROCESSED_STORE = new ConcurrentHashMap<>();

    // Tracks the latest offset committed per partition for manual tracking
    private static final Map<TopicPartition, Long> CURRENT_OFFSETS = new ConcurrentHashMap<>();

    private static final ObjectMapper objectMapper = new ObjectMapper();

    public static void main(String[] args) {

        // 1. CONFIGURATION
        Properties props = new Properties();
        props.put(ConsumerConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");
        props.put(ConsumerConfig.GROUP_ID_CONFIG, GROUP_ID);
        props.put(ConsumerConfig.KEY_DESERIALIZER_CLASS_CONFIG, StringDeserializer.class.getName());
        props.put(ConsumerConfig.VALUE_DESERIALIZER_CLASS_CONFIG, StringDeserializer.class.getName());

        // CRITICAL: Disable auto-commit. We control exactly when offsets are saved.
        props.put(ConsumerConfig.ENABLE_AUTO_COMMIT_CONFIG, "false");

        // Start reading from the beginning if no committed offset exists.
        props.put(ConsumerConfig.AUTO_OFFSET_RESET_CONFIG, "earliest");

        // Limit batch size to keep processing time predictable.
        props.put(ConsumerConfig.MAX_POLL_RECORDS_CONFIG, "10");

        // For exactly-once processing: only read committed transaction data.
        props.put(ConsumerConfig.ISOLATION_LEVEL_CONFIG, "read_committed");

        // Cooperative rebalancing to minimize downtime.
        props.put(ConsumerConfig.PARTITION_ASSIGNMENT_STRATEGY_CONFIG,
                "org.apache.kafka.clients.consumer.CooperativeStickyAssignor");

        // 2. CREATE CONSUMER
        try (KafkaConsumer<String, String> consumer = new KafkaConsumer<>(props)) {

            // 3. REBALANCE LISTENER (Know when partitions are assigned/revoked)
            ConsumerRebalanceListener rebalanceListener = new ConsumerRebalanceListener() {
                @Override
                public void onPartitionsAssigned(Collection<TopicPartition> partitions) {
                    System.out.println("✅ Partitions Assigned: " + partitions);
                    // No action needed, but good for logging.
                }

                @Override
                public void onPartitionsRevoked(Collection<TopicPartition> partitions) {
                    System.out.println("⚠️ Partitions Revoked: " + partitions + ". Committing final offsets...");
                    // Commit current offsets before losing ownership to avoid reprocessing.
                    consumer.commitSync(CURRENT_OFFSETS);
                }
            };

            // Subscribe to the topic with the listener
            consumer.subscribe(Collections.singletonList(TOPIC), rebalanceListener);

            System.out.println("🚀 Consumer started. Listening to topic: " + TOPIC);

            // 4. MAIN POLL LOOP
            while (true) {
                // Poll for new records (waits up to 1 second)
                ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(1000));

                if (records.isEmpty()) {
                    continue;
                }

                // Map to store the last offset per partition for this batch
                Map<TopicPartition, Long> offsetsToCommit = new HashMap<>();

                // Iterate through each record in the batch
                for (ConsumerRecord<String, String> record : records) {
                    TopicPartition tp = new TopicPartition(record.topic(), record.partition());

                    try {
                        // --- A) DESERIALIZATION & PROCESSING ---
                        Order order = objectMapper.readValue(record.value(), Order.class);

                        // --- B) IDEMPOTENCY CHECK (Deduplication) ---
                        if (PROCESSED_STORE.containsKey(order.getOrderId())) {
                            System.out.printf("🔄 DUPLICATE SKIPPED: Partition %d, Offset %d, Order ID %s%n",
                                    record.partition(), record.offset(), order.getOrderId());
                        } else {
                            // --- C) BUSINESS LOGIC (Idempotent Upsert) ---
                            // In real life, this would be an "INSERT ... ON DUPLICATE KEY UPDATE"
                            System.out.printf("✅ PROCESSED: Partition %d, Offset %d, Order %s%n",
                                    record.partition(), record.offset(), order);
                            PROCESSED_STORE.put(order.getOrderId(), true);
                        }

                        // Track the highest offset successfully processed for this partition
                        offsetsToCommit.put(tp, record.offset());

                    } catch (Exception e) {
                        // --- D) POISON PILL HANDLING ---
                        // If JSON parsing fails or logic fails, we DO NOT crash the loop.
                        System.err.printf("☠️ POISON PILL DETECTED! Partition: %d, Offset: %d, Value: %s %n",
                                record.partition(), record.offset(), record.value());
                        e.printStackTrace();

                        // CRITICAL: We must advance the offset past this bad record,
                        // otherwise we will read it forever. Mark this offset as "processed".
                        offsetsToCommit.put(tp, record.offset());
                    }
                } // End of for-loop

                // --- E) MANUAL OFFSET COMMIT (Atomic for the entire batch) ---
                if (!offsetsToCommit.isEmpty()) {
                    // Convert the map to OffsetAndMetadata format.
                    // Note: We commit the NEXT offset to read (offset + 1).
                    Map<TopicPartition, OffsetAndMetadata> commitMap = new HashMap<>();
                    for (Map.Entry<TopicPartition, Long> entry : offsetsToCommit.entrySet()) {
                        TopicPartition tp = entry.getKey();
                        long nextOffset = entry.getValue() + 1; // Commit the next position
                        commitMap.put(tp, new OffsetAndMetadata(nextOffset));
                        CURRENT_OFFSETS.put(tp, nextOffset); // Update local tracker
                    }

                    // Synchronous commit ensures durability. If this fails, the app logs an error.
                    consumer.commitSync(commitMap);
                    System.out.printf("💾 Committed offsets: %s%n", commitMap);
                }

            } // End while

        } catch (Exception e) {
            System.err.println("Fatal consumer error: " + e.getMessage());
        }
    }
}

This chapter demystifies the Controller, the ISR (In-Sync Replicas), the internal write path across multiple brokers, and the modern KRaft (Raft-based) metadata quorum that eliminates Zookeeper.

1. Definition (Brokers & Core Cluster Concepts)
Broker: A single Kafka server process (JVM). It stores data (partitions), handles client requests (produce/fetch), and manages replication.

Cluster: A group of brokers working together. A single broker can handle millions of reads/writes, but a cluster provides fault-tolerance and horizontal scaling.

Partition Leader: The broker responsible for handling all read and write requests for a given partition.

Partition Follower: Brokers that passively replicate data from the Leader. They fetch the latest messages and keep their logs in sync. If the Leader fails, a Follower is promoted.

ISR (In-Sync Replicas): The set of replicas (Leader + Followers) that are fully caught up with the Leader (i.e., have replicated all messages up to the Leader's Log End Offset).

Controller: One of the brokers in the cluster elected to manage the cluster metadata. It handles partition leader elections, broker membership (failover), and administrative tasks (creating/deleting topics).

KRaft (Kafka Raft): The new consensus protocol introduced in Kafka 3.0+ that replaces Zookeeper. Brokers store metadata in an internal partition (__cluster_metadata) and use a Raft quorum of controllers to manage it.

The Write Path across the Cluster (with acks=all):

Producer connects to Broker 1 (Leader for P0).

Leader (Broker 1) writes the batch to its local page cache and updates its LEO.

Followers (Broker 2 & 3) continuously fetch data from Broker 1 in the background (Follower Fetch requests).

Followers write to their own logs and update their LEOs.

Followers send back their latest LEO to the Leader.

Leader waits until all In-Sync Replicas (ISR) have updated their LEO to match the new batch.

Leader advances the High Watermark (HW) to the new offset.

Leader sends an ACK to the Producer.

3. Real-Time Usage (Why Cluster architecture matters)
High Availability (HA) in Finance: With replication.factor=3 and min.insync.replicas=2, a payment system can survive a full broker crash without losing a single transaction. The cluster auto-promotes a follower within milliseconds.

Rack Awareness: Brokers are spread across AWS Availability Zones (AZs). Kafka ensures replicas are placed in different racks (broker.rack=us-east-1a). If an entire AZ goes down, the remaining replicas elect a new leader, keeping the system online.

Rolling Upgrades: In a 3-broker cluster, you can upgrade Kafka version by killing/restarting brokers one at a time. The Controller moves leadership away from the restarting broker, ensuring zero downtime.

6. Inside the Controller and KRaft Mechanics
The Controller Duties (in KRaft):
In KRaft, the metadata is stored in the __cluster_metadata topic (partition 0). The Controller is the Active node in the Raft quorum (voted by KAFKA_CONTROLLER_QUORUM_VOTERS).

Upon a Broker Crash (e.g., Broker 3 down):

The Controller (Broker 1) detects the loss via a heartbeat timeout.

The Controller removes Broker 3 from the ISR for Partition 2 and all other partitions where it was a follower.

The Controller checks Partition 2 (where Broker 3 was the leader) and looks at the ISR list [1, 2].

It elects Broker 1 (the first in the ISR) as the new Leader.

It persists this change to the __cluster_metadata topic (using Raft consensus) so all brokers know the new state.

It sends a LeaderAndIsr request to Broker 1 and Broker 2.

Failover is complete (typically in ~5-10 seconds).

package com.kafka.admin;

import org.apache.kafka.clients.admin.AdminClient;
import org.apache.kafka.clients.admin.AdminClientConfig;
import org.apache.kafka.clients.admin.DescribeTopicsResult;
import org.apache.kafka.clients.admin.TopicDescription;
import org.apache.kafka.common.Node;
import org.apache.kafka.common.TopicPartitionInfo;

import java.util.Collections;
import java.util.Map;
import java.util.Properties;
import java.util.concurrent.ExecutionException;

public class KafkaClusterAdmin {

    private static final String BOOTSTRAP_SERVERS = "localhost:9091,localhost:9092,localhost:9093";

    public static void main(String[] args) throws ExecutionException, InterruptedException {
        Properties props = new Properties();
        props.put(AdminClientConfig.BOOTSTRAP_SERVERS_CONFIG, BOOTSTRAP_SERVERS);

        try (AdminClient admin = AdminClient.create(props)) {
            String topic = "secure-orders";

            // Describe the topic
            DescribeTopicsResult result = admin.describeTopics(Collections.singletonList(topic));
            Map<String, TopicDescription> descriptions = result.allTopicNames().get();

            TopicDescription desc = descriptions.get(topic);
            System.out.println("Topic: " + topic);
            System.out.println("Partitions: " + desc.partitions().size());

            for (TopicPartitionInfo partitionInfo : desc.partitions()) {
                Node leader = partitionInfo.leader();
                System.out.printf("  Partition %d -> Leader: %s (id=%d)%n",
                        partitionInfo.partition(),
                        leader.host() + ":" + leader.port(),
                        leader.id());

                System.out.print("    Replicas: ");
                partitionInfo.replicas().forEach(n -> System.out.print(n.id() + " "));
                System.out.println();

                System.out.print("    ISR: ");
                partitionInfo.isr().forEach(n -> System.out.print(n.id() + " "));
                System.out.println("\n");
            }

            // List all broker nodes
            System.out.println("All brokers in cluster:");
            admin.describeCluster().nodes().get()
                    .forEach(node -> System.out.printf("  Broker %d: %s:%d%n",
                            node.id(), node.host(), node.port()));
        }
    }
}

        props.put(ProducerConfig.DELIVERY_TIMEOUT_MS_CONFIG, 120000); // 2 min
        props.put(ProducerConfig.REQUEST_TIMEOUT_MS_CONFIG, 30000);   // 30 sec

        // Compression

        // Metadata refresh – forces the producer to fetch new leader info faster on failover
        props.put(ProducerConfig.METADATA_MAX_AGE_CONFIG, 5000); // 5 seconds

            AtomicInteger errorCount = new AtomicInteger(0);

            for (int i = 1; i <= 20; i++) {
                String key = "user-" + (i % 5);  // 5 distinct keys – partitions 0..4 (we have 3 partitions, so modulo 3)
                String value = String.format("{\"orderId\":\"ord-%d\", \"amount\":%d}", i, i * 100);

                                key, exception.getMessage());
                        // In production, you might retry manually, but idempotence+retries already handle it.
                    } else {
                        successCount.incrementAndGet();
                        System.out.printf("✅ Sent: key=%s, partition=%d, offset=%d%n",

                    }
                });
            }

            producer.flush();
            System.out.printf("Finished. Success: %d, Errors: %d%n",

3. Resilient Consumer with Rebalance Awareness
ClusterAwareConsumer.java – extends the Chapter 4 solution but now connects to all three brokers, uses manual commits, and logs when a partition leader changes during a rebalance.

java
package com.kafka.consumer;

import com.fasterxml.jackson.databind.ObjectMapper;
import org.apache.kafka.clients.consumer.*;
import org.apache.kafka.common.TopicPartition;
import org.apache.kafka.common.serialization.StringDeserializer;

import java.time.Duration;
import java.util.*;
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.atomic.AtomicLong;

public class ClusterAwareConsumer {

    private static final String BOOTSTRAP_SERVERS = "localhost:9091,localhost:9092,localhost:9093";
    private static final String TOPIC = "secure-orders";
    private static final String GROUP_ID = "inventory-group";

    // Simulated idempotent store (deduplication)
    private static final ConcurrentHashMap<String, Boolean> PROCESSED_STORE = new ConcurrentHashMap<>();
    // Track last committed offset per partition
    private static final Map<TopicPartition, Long> LAST_COMMITTED = new ConcurrentHashMap<>();

    private static final ObjectMapper objectMapper = new ObjectMapper();

    public static void main(String[] args) {
        Properties props = new Properties();

        // Connect to all 3 brokers
        props.put(ConsumerConfig.BOOTSTRAP_SERVERS_CONFIG, BOOTSTRAP_SERVERS);
        props.put(ConsumerConfig.GROUP_ID_CONFIG, GROUP_ID);
        props.put(ConsumerConfig.KEY_DESERIALIZER_CLASS_CONFIG, StringDeserializer.class.getName());
        props.put(ConsumerConfig.VALUE_DESERIALIZER_CLASS_CONFIG, StringDeserializer.class.getName());

        // Disable auto-commit
        props.put(ConsumerConfig.ENABLE_AUTO_COMMIT_CONFIG, "false");
        props.put(ConsumerConfig.AUTO_OFFSET_RESET_CONFIG, "earliest");
        props.put(ConsumerConfig.MAX_POLL_RECORDS_CONFIG, "10");
        props.put(ConsumerConfig.ISOLATION_LEVEL_CONFIG, "read_committed");

        // Cooperative rebalancing
        props.put(ConsumerConfig.PARTITION_ASSIGNMENT_STRATEGY_CONFIG,
                "org.apache.kafka.clients.consumer.CooperativeStickyAssignor");

        try (KafkaConsumer<String, String> consumer = new KafkaConsumer<>(props)) {

            // Rebalance listener – commits offsets before losing partitions
            ConsumerRebalanceListener listener = new ConsumerRebalanceListener() {
                @Override
                public void onPartitionsAssigned(Collection<TopicPartition> partitions) {
                    System.out.println("✅ Assigned: " + partitions);
                    // Optionally, you could read the last committed offset from a DB here.
                }

                @Override
                public void onPartitionsRevoked(Collection<TopicPartition> partitions) {
                    System.out.println("⚠️ Revoked: " + partitions + " – committing final offsets...");
                    if (!LAST_COMMITTED.isEmpty()) {
                        Map<TopicPartition, OffsetAndMetadata> commitMap = new HashMap<>();
                        LAST_COMMITTED.forEach((tp, offset) ->
                                commitMap.put(tp, new OffsetAndMetadata(offset)));
                        consumer.commitSync(commitMap);
                        System.out.println("💾 Final offsets committed.");
                    }
                }
            };

            consumer.subscribe(Collections.singletonList(TOPIC), listener);
            System.out.println("🚀 Consumer started on cluster: " + BOOTSTRAP_SERVERS);

            AtomicLong totalProcessed = new AtomicLong(0);

            while (true) {
                ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(1000));
                if (records.isEmpty()) continue;

                Map<TopicPartition, Long> offsetsToCommit = new HashMap<>();

                for (ConsumerRecord<String, String> record : records) {
                    TopicPartition tp = new TopicPartition(record.topic(), record.partition());

                    try {
                        // Deserialize JSON
                        Order order = objectMapper.readValue(record.value(), Order.class);

                        // Idempotency check
                        if (PROCESSED_STORE.putIfAbsent(order.getOrderId(), true) == null) {
                            // New order – process it
                            System.out.printf("📦 Processed: partition=%d, offset=%d, order=%s%n",
                                    record.partition(), record.offset(), order);
                            totalProcessed.incrementAndGet();
                            // In real life: do DB upsert here
                        } else {
                            System.out.printf("🔄 Duplicate skipped: partition=%d, offset=%d, id=%s%n",
                                    record.partition(), record.offset(), order.getOrderId());
                        }

                        // Track highest successful offset for this partition
                        offsetsToCommit.put(tp, record.offset());

                    } catch (Exception e) {
                        // Poison pill – log and skip
                        System.err.printf("☠️ Poison pill at partition=%d, offset=%d, value=%s%n",
                                record.partition(), record.offset(), record.value());
                        e.printStackTrace();
                        // Still advance the offset so we don't get stuck
                        offsetsToCommit.put(tp, record.offset());
                    }
                }

                // Commit offsets atomically for the whole batch
                if (!offsetsToCommit.isEmpty()) {
                    Map<TopicPartition, OffsetAndMetadata> commitMap = new HashMap<>();
                    offsetsToCommit.forEach((tp, offset) -> {
                        long next = offset + 1;
                        commitMap.put(tp, new OffsetAndMetadata(next));
                        LAST_COMMITTED.put(tp, next);
                    });
                    consumer.commitSync(commitMap);
                    System.out.printf("💾 Committed offsets: %s%n", commitMap.keySet());
                }

                System.out.printf("📊 Total processed so far: %d%n", totalProcessed.get());
            }

        } catch (Exception e) {
            System.err.println("Fatal consumer error: " + e.getMessage());
            e.printStackTrace();
        }
    }

    // Simple POJO for JSON deserialization
    static class Order {
        public String orderId;
        public int amount;

        public Order() {}

        @Override
        public String toString() {
            return "Order{id='" + orderId + "', amount=" + amount + "}";
        }
    }
}

3. Full Consumer Code (ConsumerDemo.java)

This class demonstrates:

Cooperative Rebalancing (CooperativeStickyAssignor) – minimizes the "stop-the-world" downtime during partition reassignments.

Rebalance Listener – commits offsets before partitions are revoked, preventing duplicate processing.

Manual Offset Commits (enable.auto.commit=false) – we decide exactly when to store our position.

Poison Pill Handling – catches JSON parsing errors, logs them, and commits past them so the consumer doesn't get stuck.

java
package com.kafka.consumer;

import com.fasterxml.jackson.databind.ObjectMapper;
import com.kafka.model.Order;
import org.apache.kafka.clients.consumer.*;
import org.apache.kafka.common.TopicPartition;
import org.apache.kafka.common.serialization.StringDeserializer;

import java.time.Duration;
import java.util.*;
import java.util.concurrent.ConcurrentHashMap;

public class ConsumerDemo {

    private static final String BOOTSTRAP_SERVERS = "localhost:9092";
    // private static final String BOOTSTRAP_SERVERS = "localhost:9091,localhost:9092,localhost:9093";
    private static final String TOPIC = "orders";
    private static final String GROUP_ID = "inventory-group";

    // Simulated idempotent store (e.g., Redis or DB Primary Key cache)
    private static final ConcurrentHashMap<String, Boolean> PROCESSED_STORE = new ConcurrentHashMap<>();

    public static void main(String[] args) {
        // 1. Configuration
        Properties props = new Properties();
        props.put(ConsumerConfig.BOOTSTRAP_SERVERS_CONFIG, BOOTSTRAP_SERVERS);
        props.put(ConsumerConfig.GROUP_ID_CONFIG, GROUP_ID);
        props.put(ConsumerConfig.KEY_DESERIALIZER_CLASS_CONFIG, StringDeserializer.class.getName());
        props.put(ConsumerConfig.VALUE_DESERIALIZER_CLASS_CONFIG, StringDeserializer.class.getName());

        // --- Offset Management ---
        props.put(ConsumerConfig.ENABLE_AUTO_COMMIT_CONFIG, "false");  // Manual commit
        props.put(ConsumerConfig.AUTO_OFFSET_RESET_CONFIG, "earliest"); // Start from beginning if no offset exists

        // --- Performance & Safety ---
        props.put(ConsumerConfig.MAX_POLL_RECORDS_CONFIG, "10");      // Small batches to avoid timeouts
        props.put(ConsumerConfig.ISOLATION_LEVEL_CONFIG, "read_committed"); // Only see committed transactions

        // --- COOPERATIVE REBALANCING (Minimizes downtime) ---
        props.put(ConsumerConfig.PARTITION_ASSIGNMENT_STRATEGY_CONFIG,
                "org.apache.kafka.clients.consumer.CooperativeStickyAssignor");

        // 2. Create Consumer
        try (KafkaConsumer<String, String> consumer = new KafkaConsumer<>(props)) {

            // 3. Rebalance Listener - Handles partition assignment/revocation
            ConsumerRebalanceListener rebalanceListener = new ConsumerRebalanceListener() {
                private final Map<TopicPartition, Long> currentOffsets = new ConcurrentHashMap<>();

                @Override
                public void onPartitionsAssigned(Collection<TopicPartition> partitions) {
                    System.out.println("✅ Partitions Assigned (Cooperative): " + partitions);
                    // Optionally, you could seek to a specific offset from an external DB here.
                }

                @Override
                public void onPartitionsRevoked(Collection<TopicPartition> partitions) {
                    System.out.println("⚠️ Partitions Revoked (Cooperative): " + partitions);
                    // CRITICAL: Commit the latest offsets before losing ownership.
                    // This prevents reprocessing the same messages when partitions move to another consumer.
                    if (!currentOffsets.isEmpty()) {
                        Map<TopicPartition, OffsetAndMetadata> commitMap = new HashMap<>();
                        currentOffsets.forEach((tp, offset) ->
                                commitMap.put(tp, new OffsetAndMetadata(offset + 1))); // Commit NEXT offset
                        consumer.commitSync(commitMap);
                        System.out.printf("💾 Committed final offsets: %s%n", commitMap);
                    }
                }

                // Helper to update tracked offsets for this listener instance
                public void trackOffset(TopicPartition tp, long offset) {
                    currentOffsets.put(tp, offset);
                }
            };

            // Subscribe with the listener
            consumer.subscribe(Collections.singletonList(TOPIC), rebalanceListener);

            System.out.println("🚀 Consumer started. Group: " + GROUP_ID);
            ObjectMapper mapper = new ObjectMapper();

            // 4. Main Poll Loop
            while (true) {
                // Poll for records (blocks up to 1 second)
                ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(1000));

                if (records.isEmpty()) {
                    continue;
                }

                // Map to hold the latest offset per partition for this batch
                Map<TopicPartition, Long> offsetsToCommit = new HashMap<>();

                // Iterate over each record
                for (ConsumerRecord<String, String> record : records) {
                    TopicPartition tp = new TopicPartition(record.topic(), record.partition());

                    try {
                        // --- Deserialize JSON to Order POJO ---
                        Order order = mapper.readValue(record.value(), Order.class);

                        // --- IDEMPOTENCY CHECK (Deduplication) ---
                        // Use `putIfAbsent` to atomically check if this orderId was already processed.
                        if (PROCESSED_STORE.putIfAbsent(order.getOrderId(), true) == null) {
                            // New order -> Process it
                            System.out.printf("📦 PROCESSED: partition=%d, offset=%d, order=%s%n",
                                    record.partition(), record.offset(), order);
                            // (In real life: perform DB upsert, call REST API, etc.)
                        } else {
                            // Duplicate -> Skip silently (or log)
                            System.out.printf("🔄 DUPLICATE SKIPPED: partition=%d, offset=%d, id=%s%n",
                                    record.partition(), record.offset(), order.getOrderId());
                        }

                        // Track the highest offset successfully processed for this partition
                        offsetsToCommit.put(tp, record.offset());

                    } catch (Exception e) {
                        // --- POISON PILL HANDLING ---
                        // If JSON is malformed or business logic fails, we DO NOT crash the loop.
                        System.err.printf("☠️ POISON PILL! Partition: %d, Offset: %d, RawValue: %s%n",
                                record.partition(), record.offset(), record.value());
                        e.printStackTrace();

                        // IMPORTANT: We MUST advance past this bad record.
                        // Mark the offset as processed so we don't read it forever.
                        offsetsToCommit.put(tp, record.offset());
                    }
                }

                // --- 5. MANUAL OFFSET COMMIT (Sync) ---
                // Commit the next offset for each partition (current offset + 1).
                if (!offsetsToCommit.isEmpty()) {
                    Map<TopicPartition, OffsetAndMetadata> commitMap = new HashMap<>();
                    offsetsToCommit.forEach((tp, offset) -> {
                        long nextOffset = offset + 1;
                        commitMap.put(tp, new OffsetAndMetadata(nextOffset));
                        // Update the rebalance listener's tracking map
                        rebalanceListener.trackOffset(tp, offset);
                    });

                    // Synchronous commit ensures offsets are durably stored.
                    // If this fails, the consumer will retry on the next poll.
                    consumer.commitSync(commitMap);
                    System.out.printf("💾 Committed offsets: %s%n", commitMap);
                }

            } // End while
        } catch (Exception e) {
            System.err.println("Fatal consumer error: " + e.getMessage());
            e.printStackTrace();
        }
    }
}

Welcome to Chapter 7 — Offset Management & Delivery Semantics.

This chapter tackles the most critical decision in stream processing: What happens when your consumer crashes halfway through processing a batch?

We will demystify the three delivery guarantees, illustrate the infamous "reprocess-on-crash" loop, give you a full Java application that simulates a crash to prove these patterns, and provide the CLI commands to surgically reset offsets.

1. Definition (The 3 Delivery Patterns)
Understanding the ordering of Processing vs. Offset Committing is everything.

At-most-once (Fire and forget): Commit BEFORE processing.

Result: If processing crashes, the offset is already advanced. The message is lost forever.

Use case: High-frequency metrics where losing a datapoint is acceptable for max throughput.

At-least-once (The default industry standard): Process THEN commit.

Result: If processing succeeds but commit crashes, the consumer restarts and re-reads the same message. You get duplicates, but zero data loss.

Use case: Most microservices. You handle duplicates via idempotent writes (UPSERTs).

Exactly-once (The holy grail): At-least-once + Idempotent Sink (or Kafka Transactions).

Result: You may re-process duplicates, but your output storage (DB, Elasticsearch) recognizes them and applies the update only once (e.g., INSERT ... ON DUPLICATE KEY UPDATE).

Use case: Financial ledgers, inventory management.

package com.kafka.consumer;

import com.fasterxml.jackson.databind.ObjectMapper;
import com.kafka.model.Order;
import org.apache.kafka.clients.consumer.*;
import org.apache.kafka.common.TopicPartition;
import org.apache.kafka.common.serialization.StringDeserializer;

import java.time.Duration;
import java.util.*;
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.atomic.AtomicInteger;

public class OffsetManagementDemo {

    private static final String BOOTSTRAP_SERVERS = "localhost:9092";
    private static final String TOPIC = "orders";
    private static final String GROUP_ID = "offset-demo-group";

    // Enum for delivery patterns
    public enum DeliverySemantic {
        AT_MOST_ONCE,
        AT_LEAST_ONCE,
        EXACTLY_ONCE
    }

    // Set this to change the behavior
    private static final DeliverySemantic MODE = DeliverySemantic.AT_LEAST_ONCE;

    // Simulated idempotent DB (for EXACTLY_ONCE mode)
    private static final ConcurrentHashMap<String, Boolean> IDEMPOTENT_STORE = new ConcurrentHashMap<>();

    // Crash simulation counter
    private static final AtomicInteger processedCounter = new AtomicInteger(0);
    private static final int CRASH_AFTER_RECORDS = 3; // Crash on the 3rd record

    public static void main(String[] args) {
        Properties props = new Properties();
        props.put(ConsumerConfig.BOOTSTRAP_SERVERS_CONFIG, BOOTSTRAP_SERVERS);
        props.put(ConsumerConfig.GROUP_ID_CONFIG, GROUP_ID);
        props.put(ConsumerConfig.KEY_DESERIALIZER_CLASS_CONFIG, StringDeserializer.class.getName());
        props.put(ConsumerConfig.VALUE_DESERIALIZER_CLASS_CONFIG, StringDeserializer.class.getName());
        props.put(ConsumerConfig.ENABLE_AUTO_COMMIT_CONFIG, "false");
        props.put(ConsumerConfig.AUTO_OFFSET_RESET_CONFIG, "earliest");
        props.put(ConsumerConfig.ISOLATION_LEVEL_CONFIG, "read_committed");

        try (KafkaConsumer<String, String> consumer = new KafkaConsumer<>(props)) {
            consumer.subscribe(Collections.singletonList(TOPIC));
            ObjectMapper mapper = new ObjectMapper();

            System.out.println("🚀 Starting Consumer in mode: " + MODE);
            System.out.println("⚠️  Simulated crash will trigger after processing " + CRASH_AFTER_RECORDS + " records!");

            while (true) {
                ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(1000));
                if (records.isEmpty()) continue;

                // --- 1. AT-MOST-ONCE: Commit BEFORE processing ---
                if (MODE == DeliverySemantic.AT_MOST_ONCE) {
                    // Commit the current position NOW. If we crash next, these offsets are already committed.
                    consumer.commitSync();
                    System.out.println("💾 [At-Most-Once] Committed offsets BEFORE processing.");
                }

                // Process the batch
                Map<TopicPartition, Long> offsetsToCommit = new HashMap<>();
                for (ConsumerRecord<String, String> record : records) {
                    try {
                        Order order = mapper.readValue(record.value(), Order.class);

                        // --- EXACTLY-ONCE logic: Idempotent check BEFORE processing ---
                        if (MODE == DeliverySemantic.EXACTLY_ONCE) {
                            // If this order ID already exists, we just log and skip.
                            if (IDEMPOTENT_STORE.putIfAbsent(order.getOrderId(), true) != null) {
                                System.out.printf("🔄 [Exactly-Once] Skipping duplicate: %s%n", order.getOrderId());
                                offsetsToCommit.put(new TopicPartition(record.topic(), record.partition()), record.offset());
                                continue; // Done with this record
                            }
                        }

                        // --- BUSINESS PROCESSING ---
                        System.out.printf("📦 PROCESSING: Partition=%d, Offset=%d, Order=%s%n",
                                record.partition(), record.offset(), order);

                        // Simulate a processing delay
                        Thread.sleep(100);

                        // --- CRASH SIMULATION (For At-Least-Once Test) ---
                        int currentCount = processedCounter.incrementAndGet();
                        if (currentCount == CRASH_AFTER_RECORDS) {
                            System.err.println("💥 SIMULATED CRASH! Processing stopped at record " + currentCount);
                            throw new RuntimeException("Intentional crash to test offset management!");
                        }

                        // Track successful processing for manual commit
                        offsetsToCommit.put(new TopicPartition(record.topic(), record.partition()), record.offset());

                    } catch (Exception e) {
                        // Catch poison pills etc.
                        System.err.println("Error processing record: " + record.value());
                        e.printStackTrace();
                        // In a real app, we would still advance the offset for bad records.
                        offsetsToCommit.put(new TopicPartition(record.topic(), record.partition()), record.offset());
                    }
                }

                // --- 2 & 3: AT-LEAST-ONCE & EXACTLY-ONCE: Commit AFTER processing ---
                if (MODE == DeliverySemantic.AT_LEAST_ONCE || MODE == DeliverySemantic.EXACTLY_ONCE) {
                    if (!offsetsToCommit.isEmpty()) {
                        Map<TopicPartition, OffsetAndMetadata> commitMap = new HashMap<>();
                        offsetsToCommit.forEach((tp, offset) ->
                                commitMap.put(tp, new OffsetAndMetadata(offset + 1)));

                        consumer.commitSync(commitMap);
                        System.out.println("💾 [At-Least/Exactly-Once] Committed offsets AFTER processing: " + commitMap);
                    }
                }

            } // while
        } catch (Exception e) {
            System.err.println("❌ Consumer crashed due to: " + e.getMessage());
            // The process exits. When restarted, the offset management kicks in.
        }
    }

5. Real-Time Usage (Choosing the Right Pattern)

Industry Scenario	Required Semantic	Why?
IoT Sensor Metrics	At-Most-Once	Sending 10,000 CPU readings/second. Losing 1 reading is irrelevant; throughput is king.
Email Notification Service	At-Least-Once	If the system crashes, we MUST send the email eventually. A duplicate email is preferable to a missed one (often filtered by the email provider's message-id).
Bank Account Debit/Credit	Exactly-Once	Must debit exactly once. We use transaction_id as the primary key in the database. Replays are naturally deduplicated by the DB's primary key constraint.
Kafka to HDFS (Batch)	At-Least-Once	Write to HDFS with a unique partition path. If a file is duplicated, the next compaction/merge step deduplicates based on the record key.

7. The "Commit Failure" Edge Case (Under the Hood)
What if consumer.commitSync() itself throws a TimeoutException?

If you commit in a loop (like we do), and the commit fails, we DO NOT advance the offset in memory. On the next poll(), the consumer will re-read the same batch.

This is safe for At-Least-Once, but it can lead to an infinite loop if the commit always fails (e.g., the broker is down).

Mitigation: Use commitAsync() with a callback, but note that async commits can be reordered. The most robust pattern is commitSync() with a retry limit and an exponential backoff.

The Golden Rule of Offsets:

Never commit an offset for a message you haven't successfully processed (unless using At-Most-Once). Always commit an offset that is greater than the last successfully processed message (i.e., offset + 1), so you don't re-read it.

Chapter 9 — Kafka Security Management:

Security in Apache Kafka is not a single feature—it's a layered defense strategy built on three core pillars: Encryption (protecting data in transit and at rest), Authentication (verifying identity), and Authorization (controlling access). 1. Architectural Flow Diagram (The Three-Layer Security Model)
Kafka's security architecture processes every client request through three sequential layers:

text
+------------------+     +------------------+     +------------------+     +------------------+
|                  |     |                  |     |                  |     |                  |
|   CLIENT APP     |---->|   ENCRYPTION    |---->|  AUTHENTICATION  |---->|  AUTHORIZATION   |----> KAFKA
| (Producer/       |     |   (SSL/TLS)     |     |   (SASL/mTLS)    |     |    (ACLs)        |     BROKER
|  Consumer)       |     |   Data in       |     |   Prove WHO      |     |   Determine WHAT  |
|                  |     |   Transit       |     |   you are        |     |   you can DO      |
+------------------+     +------------------+     +------------------+     +------------------+
                              │                         │                         │
                              ▼                         ▼                         ▼
                      +---------------------------------------------------------------+
                      |                     KAFKA CLUSTER                             |
                      |  +---------+  +---------+  +---------+                       |
                      |  | Broker  |  | Broker  |  | Broker  |                       |
                      |  |   1     |  |   2     |  |   3     |                       |
                      |  +---------+  +---------+  +---------+                       |
                      |                                                               |
                      |  Data at Rest Encryption (Filesystem/Disk)                   |
                      +---------------------------------------------------------------+
The Flow:

Encryption (SSL/TLS): Establishes a secure, encrypted tunnel between client and broker. All data is scrambled—eavesdroppers see only ciphertext.

Authentication (SASL/mTLS): The client presents credentials (username/password, certificate, or token) to prove its identity.

Authorization (ACLs): The broker checks the authenticated principal against Access Control Lists to determine if the requested operation (Read, Write, etc.) is permitted.

2. Encryption (Data in Transit & At Rest)
Definition
Encryption in Transit (SSL/TLS): Protects data as it travels across the network between clients and brokers. When TLS is enabled, all communication is encrypted, preventing man-in-the-middle attacks and eavesdropping. Kafka configurations still refer to this as "SSL" for historical reasons.

Encryption at Rest: Protects data stored on broker disks. Kafka does not natively encrypt messages at the partition-file level—this is typically handled via filesystem-level encryption (LUKS, AWS EBS encryption) or application-level field encryption for sensitive PII data.

Hands-On: Configuring SSL/TLS for a Kafka Broker
Step 1: Generate the Keystore and Truststore
The Keystore holds the server's private key and certificate. The Truststore holds trusted CA certificates.

bash
# 1. Generate the server keystore (JKS format)
keytool -keystore kafka.server.keystore.jks -alias localhost -validity 365 -genkey -keyalg RSA

# 2. Create a Certificate Authority (CA)
openssl req -new -x509 -keyout ca-key -out ca-cert -days 365

# 3. Export the server certificate from the keystore
keytool -keystore kafka.server.keystore.jks -alias localhost -certreq -file cert-file

# 4. Sign the certificate with the CA
openssl x509 -req -CA ca-cert -CAkey ca-key -in cert-file -out cert-signed -days 365 -CAcreateserial

# 5. Import the CA into the server truststore
keytool -keystore kafka.server.truststore.jks -alias CARoot -import -file ca-cert

# 6. Import the signed certificate back into the keystore
keytool -keystore kafka.server.keystore.jks -alias localhost -import -file cert-signed

4. Authorization (Access Control)
Definition
Authorization answers: "What are you allowed to do?" Kafka uses Access Control Lists (ACLs) to enforce fine-grained permissions. An ACL is defined as: "Principal P is [Allowed/Denied] Operation O From Host H on Resource R".

ACL Operations include: Read, Write, Create, Delete, Describe, Alter, All.

ACL Resources include: Topic, Group, Cluster, TransactionalId.

Step 2: Add ACLs Using the CLI

  --add --allow-principal User:producer-user \
  --operation Write --topic orders

# Allow 'consumer-user' to READ from topic 'orders' and COMMIT offsets

package producer;

import com.launchdarkly.eventsource.EventHandler;
import com.launchdarkly.eventsource.MessageEvent;
import org.apache.kafka.clients.producer.KafkaProducer;
import org.apache.kafka.clients.producer.ProducerRecord;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

public class WikimediaChangeHandler implements EventHandler {

    private static final Logger log = LoggerFactory.getLogger(WikimediaChangeHandler.class);
    private final KafkaProducer<String, String> producer;
    private final String topic;

    public WikimediaChangeHandler(KafkaProducer<String, String> producer, String topic) {
        this.producer = producer;
        this.topic = topic;
    }

    @Override
    public void onOpen() {
        log.info("SSE connection to Wikimedia opened.");
    }

    @Override
    public void onClosed() {
        log.info("SSE connection to Wikimedia closed.");
    }

    @Override
    public void onMessage(String event, MessageEvent messageEvent) {
        String data = messageEvent.getData();
        if (data == null || data.isEmpty()) {
            return;
        }

        // Asynchronously send the raw JSON to Kafka
        producer.send(new ProducerRecord<>(topic, data), (metadata, exception) -> {
            if (exception != null) {
                log.error("Failed to send message to Kafka: {}", exception.getMessage());
            } else {
                log.debug("Sent to Kafka. Partition: {}, Offset: {}", metadata.partition(), metadata.offset());
            }
        });
    }

    @Override
    public void onComment(String comment) {
        // Ignore SSE comments
    }

    @Override
    public void onError(Throwable t) {
        log.error("Error in SSE stream: {}", t.getMessage());
    }
}

package consumer;

import com.fasterxml.jackson.databind.JsonNode;
import com.fasterxml.jackson.databind.ObjectMapper;
import org.apache.http.HttpHost;
import org.apache.kafka.clients.consumer.ConsumerConfig;
import org.apache.kafka.clients.consumer.ConsumerRecords;
import org.apache.kafka.clients.consumer.KafkaConsumer;
import org.apache.kafka.common.serialization.StringDeserializer;
import org.opensearch.action.index.IndexRequest;
import org.opensearch.action.index.IndexResponse;
import org.opensearch.client.RequestOptions;
import org.opensearch.client.RestClient;
import org.opensearch.client.RestHighLevelClient;
import org.opensearch.common.xcontent.XContentType;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

import java.time.Duration;
import java.util.List;
import java.util.Properties;

public class OpenSearchConsumer {

    private static final Logger log = LoggerFactory.getLogger(OpenSearchConsumer.class);
    private static final ObjectMapper mapper = new ObjectMapper();

    public static void main(String[] args) {
        log.info("Starting OpenSearch Consumer...");

        // 1. Load configs
        Properties props = new Properties();
        try (var input = OpenSearchConsumer.class.getClassLoader()
                .getResourceAsStream("application.properties")) {
            props.load(input);
        } catch (Exception e) {
            log.error("Failed to load properties", e);
            System.exit(1);
        }

        // Consumer-specific overrides
        props.put(ConsumerConfig.KEY_DESERIALIZER_CLASS_CONFIG, StringDeserializer.class.getName());
        props.put(ConsumerConfig.VALUE_DESERIALIZER_CLASS_CONFIG, StringDeserializer.class.getName());
        props.put(ConsumerConfig.ENABLE_AUTO_COMMIT_CONFIG, "false"); // Manual commit
        props.put(ConsumerConfig.GROUP_ID_CONFIG, "opensearch-consumer-group");

        // 2. Set up OpenSearch Client
        try (RestHighLevelClient opensearchClient = new RestHighLevelClient(
                RestClient.builder(new HttpHost("localhost", 9200, "http")))) {

            // 3. Create Kafka Consumer
            try (KafkaConsumer<String, String> consumer = new KafkaConsumer<>(props)) {
                consumer.subscribe(List.of("wikimedia.recentchange"));

                while (true) {
                    ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(1000));

                    if (records.isEmpty()) {
                        continue;
                    }

                    records.forEach(record -> {
                        try {
                            String json = record.value();

                            // Parse to extract a unique ID for deduplication in OpenSearch
                            JsonNode jsonNode = mapper.readTree(json);
                            String id = jsonNode.path("meta").path("id").asText();

                            // If no ID, fallback to partition+offset to avoid duplicates
                            if (id == null || id.isEmpty()) {
                                id = record.topic() + "_" + record.partition() + "_" + record.offset();
                            }

                            // Build Index Request
                            IndexRequest request = new IndexRequest("wikimedia")
                                    .id(id)
                                    .source(json, XContentType.JSON);

                            IndexResponse response = opensearchClient.index(request, RequestOptions.DEFAULT);
                            log.debug("Indexed to OpenSearch: ID={}, Result={}", id, response.getResult());

                        } catch (Exception e) {
                            log.error("Failed to index record: {} | Error: {}",
                                    record.value(), e.getMessage());
                        }
                    });

                    // Commit offsets after successful processing
                    consumer.commitSync();
                    log.info("{} records processed and committed.", records.count());
                }
            }

        } catch (Exception e) {
            log.error("Fatal error in consumer", e);
        }
    }
}

package streams;

import com.fasterxml.jackson.databind.JsonNode;
import com.fasterxml.jackson.databind.ObjectMapper;
import org.apache.kafka.common.serialization.Serde;
import org.apache.kafka.common.serialization.Serdes;
import org.apache.kafka.streams.StreamsBuilder;
import org.apache.kafka.streams.kstream.Consumed;
import org.apache.kafka.streams.kstream.Grouped;
import org.apache.kafka.streams.kstream.KStream;
import org.apache.kafka.streams.kstream.Produced;

public class BotCountStreamBuilder {

    private static final ObjectMapper mapper = new ObjectMapper();

    public void buildPipeline(StreamsBuilder builder) {
        Serde<String> stringSerde = Serdes.String();

        KStream<String, String> sourceStream = builder.stream(
                "wikimedia.recentchange",
                Consumed.with(stringSerde, stringSerde)
        );

        // Extract bot flag: "bot" or "human"
        KStream<String, String> botFlagStream = sourceStream.mapValues(value -> {
            try {
                JsonNode json = mapper.readTree(value);
                boolean isBot = json.path("bot").asBoolean(false);
                return isBot ? "bot" : "human";
            } catch (Exception e) {
                return "unknown";
            }
        });

        // Group by flag and count
        botFlagStream
                .groupByKey(Grouped.with(stringSerde, stringSerde))
                .count()
                .toStream()
                .to("wikimedia.bot.count", Produced.with(stringSerde, Serdes.Long()));
    }
}

package streams;

import com.fasterxml.jackson.databind.JsonNode;
import com.fasterxml.jackson.databind.ObjectMapper;
import org.apache.kafka.common.serialization.Serde;
import org.apache.kafka.common.serialization.Serdes;
import org.apache.kafka.streams.StreamsBuilder;
import org.apache.kafka.streams.kstream.Consumed;
import org.apache.kafka.streams.kstream.Grouped;
import org.apache.kafka.streams.kstream.KStream;
import org.apache.kafka.streams.kstream.Produced;

public class WebsiteCountStreamBuilder {

    private static final ObjectMapper mapper = new ObjectMapper();

    public void buildPipeline(StreamsBuilder builder) {
        Serde<String> stringSerde = Serdes.String();

        KStream<String, String> sourceStream = builder.stream(
                "wikimedia.recentchange",
                Consumed.with(stringSerde, stringSerde)
        );

        // Extract website domain (e.g., "en.wikipedia.org")
        KStream<String, String> websiteStream = sourceStream.mapValues(value -> {
            try {
                JsonNode json = mapper.readTree(value);
                // Wikimedia uses 'meta' -> 'uri' or directly 'server_name'
                String serverName = json.path("server_name").asText();
                if (serverName == null || serverName.isEmpty()) {
                    serverName = json.path("meta").path("domain").asText();
                }
                return serverName != null ? serverName : "unknown";
            } catch (Exception e) {
                return "unknown";
            }
        });

        websiteStream
                .groupByKey(Grouped.with(stringSerde, stringSerde))
                .count()
                .toStream()
                .to("wikimedia.website.count", Produced.with(stringSerde, Serdes.Long()));
    }
}

package streams;

import org.apache.kafka.common.serialization.Serde;
import org.apache.kafka.common.serialization.Serdes;
import org.apache.kafka.streams.StreamsBuilder;
import org.apache.kafka.streams.kstream.Consumed;
import org.apache.kafka.streams.kstream.Grouped;
import org.apache.kafka.streams.kstream.KStream;
import org.apache.kafka.streams.kstream.Materialized;
import org.apache.kafka.streams.kstream.Produced;
import org.apache.kafka.streams.kstream.TimeWindows;
import org.apache.kafka.streams.kstream.Windowed;

import java.time.Duration;

public class EventCountTimeseriesBuilder {

    public void buildPipeline(StreamsBuilder builder) {
        Serde<String> stringSerde = Serdes.String();
        Serde<Long> longSerde = Serdes.Long();

        KStream<String, String> sourceStream = builder.stream(
                "wikimedia.recentchange",
                Consumed.with(stringSerde, stringSerde)
        );

        // Use a constant key "all" to group all events together for global time-series
        sourceStream
                .mapValues(value -> "all") // Static key for global aggregation
                .groupByKey(Grouped.with(stringSerde, stringSerde))
                .windowedBy(TimeWindows.ofSizeWithNoGrace(Duration.ofMinutes(1)))
                .count(Materialized.with(stringSerde, longSerde))
                .toStream()
                .map((Windowed<String> key, Long count) -> {
                    // Format the window key to a readable string
                    String windowStart = key.window().startTime().toString();
                    return new org.apache.kafka.streams.KeyValue<>(
                            windowStart,
                            count.toString()
                    );
                })
                .to("wikimedia.timeseries", Produced.with(stringSerde, stringSerde));
    }
}
